## 一、产品概述

### 1.1 一句话定义

浏览器直访的多账号签到与 AI 资源调度一站式工作台：支持 **Trae / WorkBuddy（CodeBuddy）** 双账号体系的账号管理、每日自动签到、积分看板、JWT 自动续期，内嵌 **OpenAI / Anthropic / Codex Responses 三协议兼容 API 网关**，单进程 axum 服务承载管理面 + 网关 + 调度器，Docker 一键部署。

### 1.2 现状与痛点（Web 版视角）

| 痛点 | 本产品解法 |
|---|---|
| Trae/WorkBuddy 签到、成长中心任务需要每天人工登录多个客户端操作 | 内置调度器每日 7 任务全自动（签到/续期/模型同步/快照），服务器无人值守 |
| 积分余额变化不透明，消耗难以追踪 | 每日快照自动采集 + 近 30 天三线趋势 + 官方请求用量对账 |
| 单账号积分有限，需要多账号轮换供 API 消费 | 三池调度（Trae/WorkBuddy/自定义）+ 多策略轮换 + 会话粘性 + 冷却熔断 |
| AI 编码工具（Claude Code/Codex CLI）需要统一接入点 | 三协议兼容网关 + ck_ 子 Key 配额 + 四段模型路由 |
| 服务器上跑但没人盯着，任务失败了不知道 | Bark / Server酱 / Webhook 三渠道通知（签到完成/任务失败） |

### 1.3 产品目标

1. **无人值守**：签到、续期、快照全自动化，故障自动重试，结果可通知、可查询；
2. **积分为本**：把签到获得的积分高效转化为 API 供给（多账号池化轮换）；
3. **零门槛部署**：`docker compose up` 一次成功，浏览器任意设备直访；
4. **数据自主**：全部数据存服务端本地 SQLite，出网仅上游官方接口。

### 1.4 目标用户

- 持有多个 Trae / WorkBuddy 账号、希望自动化签到与积分管理的个人用户；
- 需要 AI 编码工具（Claude Code、Codex CLI、CC Switch 生态）稳定 API 供给的开发者；
- 具备基础 Docker 运维能力的技术用户。

> **合规边界**：仅管理本人合法持有的账号；不破解、不绕过付费；与 Trae / WorkBuddy 官方无关联。

## 三、界面设计

### 3.1 设计语言

- **风格**：紧凑现代，Tailwind 3 工具类；amber（琥珀）为强调主色；6 套主题（石墨灰/炭黑/暗夜紫/墨绿/琥珀暖夜/科技蓝，默认炭黑），`data-theme` 驱动，支持暗色模式；
- **交互纪律**：所有异步按钮最少 1 秒 loading（`withMinDelay`）+ Toaster 成功/失败反馈；确认操作用自定义 Modal（禁 `window.confirm`）；中文优先，支持中英双语；
- **红涨绿跌**：积分/额度数值配色遵循国内习惯。

### 3.2 信息架构

登录页（token 登录，HttpOnly cookie 7 天）→ 主界面左侧边栏导航：

```
概览（Dashboard）      — 账号签到状态总览 + 调度任务执行状态
账号管理（Accounts）   — Trae 账号 CRUD/分组/OAuth/导入导出
Buddy 账号             — WorkBuddy 账号池/OAuth/导入导出
一键签到（Checkin）    — 双端批量签到（SSE 实时进度）
积分看板（Credits）    — Trae 趋势 / WB 积分与用量
API 服务（ApiService） — 网关池/策略/模型目录/子 Key/用量
日志（Logs）           — 签到/网关/应用日志
系统设置（左下角）     — 外观/语言/WB 设置/网关设置 + 安全与管理（通知渠道/IP允许列表/管理员令牌）
```

### 3.3 关键页面要点

- **概览**：签到状态卡片（成功/已签/失败/冷却分布）、调度器 7 任务最近执行（时间+摘要+成败）、快捷入口；
- **账号管理**：列表（掩码 JWT/积分/冷却/今日签到状态）+ 分组侧栏 + OAuth 弹窗（三步粘贴指引）+ 导入预览弹窗（重复标记/分组合并预览）；
- **一键签到**：范围选择（全部/分组/手动勾选）+ 选项（跳过已签/过期）+ 进度流（SSE 逐账号推送）+ 趋势图；
- **积分看板**：Trae 三线趋势（总数/获得/消耗，快照数据）+ WB 积分三件套/官方用量（31 天分页聚合）/Token 统计（缓存命中率/热力图，明示口径）；
- **API 服务**：池状态五态机可视化 + 账号池勾选与策略 + 调度策略（smart 说明/priority 拖序/per_model 覆盖）+ 模型目录（人工维护标 `*`）+ 子 Key 管理 + 用量统计（7/14/30 天 + 模型 Top5 + 请求日志）。

## 四、关键交互流程

### 4.1 首次部署（新用户 4 步接入）

```
docker compose up -d --build → 读取 admin_token → 浏览器登录
  → 账号管理 OAuth 录入（Trae 粘贴回调 / WB 扫码轮询）或导入 JSON
  → 一键签到 / 等待每日调度自动执行
```

### 4.2 日常运行（零人工）

```
05:30 JWT 续期 → 09:00/09:10 双端签到 → 10:30 WB 续期
  → 全天网关服务（池调度/粘性/冷却自动处理）
  → 23:30/23:40 积分快照 → 签到完成/任务失败 → 通知推送
失败任务：30 分钟冷却自动重试；重启自动补跑当天错过的任务
```

### 4.3 JWT 续期链

OAuth 账号（有 refresh_token）：调度任务 05:30 遍历账号，JWT 剩余 < 48h 才真正发起刷新（lazy gate，未临期零网络请求）；refresh_token 被吊销 → 账号标记「需重新 OAuth」，人工重新录入。

### 4.4 网关请求处理链

```
客户端请求 → 鉴权（ck_ Key 白名单/专一/配额）→ 模型路由（四段）
  → 池间调度（smart/priority/per_model + fallback）
  → 池内取号（策略过滤：冷却/禁用/过期；粘性绑定优先）
  → 协议适配（WB 改写/指纹清洗/重试计划）→ 上游 SSE
  → 协议投影（OpenAI/Anthropic/Responses 三态输出）→ 用量落库
```

## 五、数据模型

- **存储**：SQLite 单库（WAL），`AIWORK_DATA_DIR/data/aiwork.sqlite`；kv 文档表 + 行文档实体表 + 列化流水表三类（详见 tech-framework.md §3）；
- **敏感数据**：Trae jwt/refresh_token 入 Stronghold vault（`conf/vault.stronghold`，主密钥 `vault_key.bin` 或 env）；WB 凭据入 `wb_tokens` 表；列表接口一律掩码下发，完整值按需获取；
- **账号唯一性**：Trae 以 Cloud-IDE uid 为主键（dc uid 与 Cloud-IDE uid 是两套体系，红线不可混用）；WB 账号 id = `wb-<sha256(token)前12位>`（同 token 稳定同 id）；
- **备份边界**：`data/` 整目录 + `conf/vault_key.bin`（丢失 = 凭据不可解密）。

## 六、非功能需求

| 维度 | 要求 |
|---|---|
| 部署 | Docker 多阶段构建一次成功；HEALTHCHECK 30s 探活；升级不丢数据（volume） |
| 安全 | 管理面单管理员 + HttpOnly cookie；网关 fail-closed；凭据掩码 + vault 加密；建议反代 TLS + IP 允许列表 |
| 性能 | 网关流式首字 10s 故障转移；SSE keep-alive 15s；池调度 100ms 防惊群；SQLite 单连接串行足够单机负载 |
| 可靠 | 任务 panic 捕获不影响调度；通知旁路失败不阻塞主流程；失败冷却重试；重启补跑 |
| 合规 | 零外发（不出网到任何自有后端）；免责声明；凭证脱敏红线（上游 prompt/input 不复制） |

## 七、风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 上游接口/风控变化 | 高 | 协议层独立模块 + 单测锁定；宽容解析；合成指纹无硬件绑定 |
| vault_key 丢失 | 高 | 文档强制备份；丢失需重新录入账号 |
| OAuth 粘贴模式用户困惑 | 中 | 三步指引文案 + 明示「无法连接页是预期现象」 |
| 容器时区漂移 | 中 | 镜像 tzdata + TZ 强制；启动补跑兜底 |
| 桌面老用户升级断裂 | 中 | 独立产品线；导出→导入迁移指引；老 vault 不可迁移明示 |
